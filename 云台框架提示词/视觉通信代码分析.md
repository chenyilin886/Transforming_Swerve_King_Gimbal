# 视觉通信代码分析

## 1. 总体结论

当前工程中，视觉通信并不是实现于 `APP/Vision/vision.cpp` 或 `APP/Vision/vision.hpp`。这两个文件存在但内容为空。实际承担视觉通信逻辑的是 `Task/CommunicationTask.hpp` 与 `Task/CommunicationTask.cpp`，并在云台控制、发射控制、CAN 回调和硬件初始化等模块中被调用。

核心通信链路可以概括为：

- USB CDC 与上位机/视觉端进行双向数据交换。
- 周期任务每 4 ms 向视觉端发送云台姿态、弹速、敌方颜色和模式信息。
- 同一周期内轮询接收视觉端返回的目标 pitch/yaw、开火标志、瞄准点和时间戳。
- 云台任务读取视觉目标角度，用 PID/ADRC 控制 yaw 与 pitch 电机。
- 发射任务读取视觉开火标志，用于更新射击状态机。
- 云台到 chassis 的 CAN 通信还会携带视觉 `aim_x`、`aim_y` 等信息。

## 2. 周期通信任务

`CommunicationTask()` 是视觉通信的调度入口，任务循环中依次执行：

```cpp
Communicat::vision.Data_send();
Communicat::vision.dataReceive();
Gimbal_to_Chassis_Data.Data_send();
osDelay(4);
```

这说明视觉通信周期约为 4 ms。每轮循环先向视觉端发送数据，再接收视觉端数据，然后发送云台到 chassis 的 CAN 数据。

从调度结构看，视觉通信和云台到 chassis 的通信被放在同一个任务中处理，说明该项目把“对外通信”集中在 `CommunicationTask` 中，而不是按功能模块分别放在 `APP/Vision`、`APP/Chassis` 等目录中。

## 3. 发送给视觉端的数据帧

发送逻辑实现于 `Vision::Data_send()`。

发送接口为 USB CDC：

```cpp
CDC_Transmit_FS(Tx_pData, Vision::TX_FRAME_SIZE);
```

其中：

```cpp
TX_FRAME_SIZE = TX_PAYLOAD_SIZE + 2 = 29;
```

发送帧格式如下：

| 字节位置 | 含义 |
|---|---|
| 0-1 | 帧头 `0x39 0x39` |
| 2-5 | `quat_w`，float 原始内存拷贝 |
| 6-9 | `quat_x`，float 原始内存拷贝 |
| 10-13 | `quat_y`，float 原始内存拷贝 |
| 14-17 | `quat_z`，float 原始内存拷贝 |
| 18-21 | `bullet_rate`，float，来自 `Gimbal_to_Chassis_Data.getLaunchSpeed()` |
| 22 | `enemy_color`，当前固定为 `0x52` |
| 23 | `vision_mode` |
| 24 | 帧尾 `0xFF` |
| 25-28 | 本地 `send_time`，大端字节序 |

该函数还会计算时间差：

```cpp
demo_time = tx_gimbal.time - rx_target.time;
```

这用于估算发送端时间和视觉端回传时间之间的延迟。

## 4. 接收视觉端的数据帧

接收逻辑实现于 `Vision::dataReceive()`。

接收接口为：

```cpp
CDC_Receive_FS(Rx_pData, &rx_len);
```

期望接收长度为 19 字节。当前代码只检查帧头：

```cpp
if (Rx_pData[0] == 0x39 && Rx_pData[1] == 0x39)
```

视觉回传帧格式如下：

| 字节位置 | 含义 |
|---|---|
| 0-1 | 帧头 `0x39 0x39` |
| 2-5 | pitch 角度，int32 大端，除以 100.0 |
| 6-9 | yaw 角度，int32 大端，除以 100.0 |
| 10 | `vision_ready` |
| 11 | `fire` |
| 12 | tail |
| 13-16 | 视觉端返回时间戳 |
| 17 | `aim_x` |
| 18 | `aim_y` |

解析后，代码会对 yaw 和 pitch 做符号翻转：

```cpp
yaw_angle_ = rx_target.yaw_angle;
pitch_angle_ = rx_target.pitch_angle;
pitch_angle_ *= -1.0;
yaw_angle_ *= -1.0;
```

因此：

- `getTarYaw()` / `getTarPitch()` 返回的是翻转后的目标角度。
- `getVisionYaw()` / `getVisionPitch()` 返回的是视觉端原始角度。

## 5. 云台控制中的视觉数据使用

在 `Task/GimbalTask.cpp` 中，`GIMBAL::VISION` 模式会读取视觉目标角度。

Yaw 控制中使用：

```cpp
filter_tar_yaw_pos = Communicat::vision.getTarYaw();
```

Pitch 相关代码中既出现了：

```cpp
filter_tar_pitch = Communicat::vision.getVisionPitch();
```

也出现了：

```cpp
Communicat::vision.getTarPitch()
```

这里存在一个值得注意的语义不一致：yaw 使用的是符号翻转后的 `getTarYaw()`，而 pitch 在部分位置使用原始值 `getVisionPitch()`，后续控制又使用 `getTarPitch()`。如果外部视觉端输出坐标系已经固定，这里需要重点确认 pitch 的符号约定是否一致。

Yaw 控制链路大致为：

1. 读取视觉 yaw 目标角。
2. 使用 `Tools.Zero_crossing_processing()` 处理角度跨零问题。
3. 角度 PID 输出目标 yaw 速度。
4. `Adrc_yaw_vision` 速度环输出力矩。
5. 通过 DM4310 控制 yaw 电机：

```cpp
BSP::Motor::DM::Motor4310.ctrl_Mit(2, 0, 0, 0, 0, target_torque);
```

Pitch 控制链路大致为：

1. 读取视觉 pitch 目标角。
2. 角度 PID 输出目标 pitch 速度。
3. `Adrc_pitch_vision` 速度环结合重力前馈输出力矩。
4. 通过 DM4310 控制 pitch 电机：

```cpp
BSP::Motor::DM::Motor4310.ctrl_Mit(1, 0, 0, 0, 0, target_torque);
```

## 6. 发射控制中的视觉开火标志

视觉端回传帧中的第 11 字节被解析为 `fire`：

```cpp
Rx_pData[11]
```

代码还维护了 `fire_update_count`，用于统计 fire 状态变化次数。

在 `ShootTask.cpp` 中，发射状态机会读取视觉开火信息：

```cpp
Communicat::vision.time_demo();
TASK::Shoot::shoot_fsm.setFireFlag(Communicat::vision.get_fire_num());
```

这说明视觉端不仅负责给出目标角度，也参与自动发射决策。

## 7. 云台到 Chassis 的 CAN 通信

`Gimbal_to_Chassis::Data_send()` 会发送两帧 CAN2 数据：

- `CAN_G2C_FRAME1_ID = 0x205`
- `CAN_G2C_FRAME2_ID = 0x206`

发送内容包括：

- 遥控器/键鼠移动量 `LX`、`LY`
- 小陀螺或旋转速度
- yaw 角度误差
- chassis 模式位
- UI 标志位
- 视觉 `aim_x`、`aim_y`
- 剩余弹丸数量等

`Gimbal_to_Chassis::HandleCANMessage()` 负责解析 chassis 发回云台的数据：

- `0x207`，帧头 `0x21 0x12`：热量、冷却等信息。
- `0x208` 或 `0x207`：发射速度信息。

其中 chassis 回传的 launch speed 会进入：

```cpp
Gimbal_to_Chassis_Data.getLaunchSpeed()
```

随后作为 `bullet_rate` 发送给视觉端，用于视觉弹道预测或解算。

## 8. 硬件回调与初始化

`Task/CallBack.cpp` 中包含主要外设回调：

- CAN1 FIFO0：解析 DM 电机反馈。
- CAN2 FIFO1：解析 DJI 电机反馈，并调用：

```cpp
Gimbal_to_Chassis_Data.HandleCANMessage(rx_frame2.id, rx_frame2.data, rx_frame2.dlc);
```

- UART3 idle：解析 DR16 遥控器。
- UART1 idle：解析 IMU。

`BSP/Init.cpp` 中启动了 IMU 和遥控器的 UART DMA idle 接收，并初始化 IMU。

这部分说明视觉通信虽然走 USB CDC，但它依赖 IMU 姿态、chassis 回传弹速、遥控器状态和云台电机反馈共同闭环。

## 9. 主要风险与可改进点

### 9.1 视觉代码位置不直观

`APP/Vision/vision.cpp` 与 `APP/Vision/vision.hpp` 是空文件，实际实现却在 `Task/CommunicationTask.*` 中。后续维护者很容易误判视觉模块未实现。

建议：

- 将 `Vision` 类拆回 `APP/Vision`。
- `CommunicationTask` 只保留周期调度逻辑。

### 9.2 接收校验偏弱

当前接收只判断帧头，不检查：

- `rx_len` 是否等于 19。
- 帧尾是否正确。
- 是否存在 CRC 或 checksum。
- 时间戳或序号是否连续。

建议至少增加长度和帧尾校验。如果比赛环境干扰较强，建议增加 CRC8/CRC16。

### 9.3 发送和接收协议编码不对称

发送四元数和弹速时直接拷贝 float 内存，而接收 pitch/yaw 时使用 int32 大端并除以 100。

这要求视觉端严格匹配 MCU 的 float 字节序和对齐方式。若视觉端运行在 PC 或不同平台，建议明确协议文档，避免大小端或 float 表示差异导致解析错误。

### 9.4 `time_demo()` 判断条件疑似错误

当前逻辑中存在：

```cpp
if (demo_time > 20 || demo_time < 200)
```

该条件几乎总为真。更合理的写法可能是：

```cpp
if (demo_time > 20 && demo_time < 200)
```

需要结合原始意图确认。

### 9.5 时间差计算时机可能不稳

`Data_send()` 中会从 `Rx_pData[13..16]` 计算上一帧回传时间，但这发生在新的接收帧被完整校验之前。如果 `Rx_pData` 中残留旧数据或异常数据，延迟计算可能失真。

建议把视觉回传时间戳解析放在 `dataReceive()` 且通过校验后更新。

### 9.6 Pitch 符号使用需要统一

云台视觉模式中 pitch 有时使用原始视觉值，有时使用翻转后的目标值。建议统一约定：

- 若控制器需要云台坐标系角度，则统一使用 `getTarPitch()`。
- 若只是调试显示视觉端原始输出，则使用 `getVisionPitch()`。

### 9.7 USB CDC 接收方式可能需要确认

当前代码在周期任务中主动调用 `CDC_Receive_FS()`。如果工程使用的是标准 STM32 USB CDC callback 模式，接收通常由 USB 中断/回调驱动，而不是任务中轮询调用。

建议确认 `CDC_Receive_FS()` 的具体实现，避免出现覆盖缓冲区、重复启动接收或漏帧问题。

## 10. 总结

这套视觉通信的核心思路是：云台周期性向视觉端发送姿态和弹速，视觉端回传目标角度、开火标志和瞄准点，云台控制任务再根据这些数据闭环控制 yaw/pitch 电机，同时发射任务根据视觉 fire 标志更新射击状态。

当前实现能体现完整链路，但模块边界和协议健壮性还有提升空间。最优先建议处理三件事：

1. 把视觉通信实现从 `CommunicationTask` 中拆分回 `APP/Vision`，让模块职责更清晰。
2. 为接收帧增加长度、帧尾和 CRC 校验。
3. 统一 pitch/yaw 的符号约定，尤其是 `getVisionPitch()` 与 `getTarPitch()` 的使用边界。
